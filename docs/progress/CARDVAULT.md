# CardVault — точка продолжения разработки

**Обновлено:** 27 октября 2026 года.

Это состояние реализации, а не описание целевой архитектуры. Целевые границы определены в [ARCHITECTURE.md](../ARCHITECTURE.md), [ADR 0001](../decisions/0001-cardvault-and-provider-connector.md) и [ADR 0002](../decisions/0002-merchant-authentication-at-gateway.md).

## Что реализовано

- Один ASP.NET Core проект с организацией по функциональным срезам.
- StoredCard: принадлежность мерчанту, необязательная ссылка на покупателя, зашифрованный PAN, последние четыре цифры, срок действия и состояние карты. CVV в сущности отсутствует.
- Шифрование PAN через HTTP-клиент Vault Transit; SQL Server хранит шифротекст и метаданные. Настроены DbContext, EF-конфигурации, миграции и аудит дат.
- CardRegistrationSession: хеш случайного токена, мерчант, покупатель, срок действия, состояние, результат StoredCardId и Version для контроля конкуренции.
- Прикладной обработчик создания сессии. Исходный токен возвращается при выдаче, в БД хранится только SHA-256.
- Аутентификация регистрационного Bearer-токена, отдельная политика доступа и доверенный CardRegistrationContext.
- Подключён `POST /cards`: проверка реквизитов, шифрование, атомарное сохранение карты и завершения сессии одним SaveChangesAsync.
- Повтор завершённой регистрации возвращает прежний результат, пока разрешение действует. При конфликте версии несохранённые изменения отбрасываются, результат перечитывается без повторного шифрования или сохранения.
- Локальный HTTP-маппер Error и централизованная обработка исключений без отдельной общей библиотеки.
- Публичный OpenAPI `public-v1` с описанием регистрационного токена. Gateway публикует документ в Scalar. Дополнительный Scalar в Aspire настроен на HTTPS с допуском сертификата разработки только в Development.

Проверена доступность OpenAPI CardVault по HTTPS: документ возвращал `200` и содержал `/cards`; пользователь подтвердил загрузку Scalar после исправления HTTPS-настроек. Это не подтверждает прохождение полного сценария регистрации карты или конкурентных запросов.

## На чём остановились

HTTP endpoint `POST /card-registration-sessions` ещё не подключён: сначала нужен доверенный MerchantId от Gateway. Маршрут в Gateway и прикладной обработчик выдачи уже есть, но внешнему backend пока неоткуда получить сессию через завершённый HTTP-сценарий.

CardVault не будет реализовывать проверку API-ключей мерчанта. Решено перейти к минимальному настоящему Merchants, затем подключить аутентификацию Gateway по ADR 0002. Development-заглушка проверки ключей для текущего этапа не выбрана. Локальный Development-режим без mTLS остаётся отдельным согласованным механизмом транспортного доверия, а не заменой Merchants.

## Что сделать при возвращении

1. Добавить приём внутреннего контекста Gateway: проверить доверие к вызывающему сервису и строго прочитать `X-Way2Pay-Merchant-Id`. Доверенный MerchantId не берётся из тела запроса.
2. Подключить HTTP-выдачу регистрационной сессии с отдельной политикой доступа. Использовать существующий обработчик; ответ с токеном не кешировать.
3. Дополнить OpenAPI и пройти сценарий «проверка ключа в Merchants → Gateway → выдача сессии → регистрация карты», включая повтор запроса и недействующее разрешение.
4. Согласовать размещение JS-формы, способ её встраивания и протокол передачи токена и результата, затем реализовать форму сохранения карты. Iframe обсуждался как предложение; его origin-привязки и протокол ещё не утверждены.

CVV-сессии, раскрытие реквизитов Connector, провайдерские токены и сам Connector не относятся к завершённому блоку регистрации. Их контракты и реализация остаются отдельными задачами. Автоматизированных тестов пока нет; статическая проверка изменений не заменяет проверку исполнения.
