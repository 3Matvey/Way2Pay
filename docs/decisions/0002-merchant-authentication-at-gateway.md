# ADR 0002. Аутентификация мерчантов в Gateway

**Статус:** согласованная целевая архитектура; не является подтверждением готовности реализации.

**Дата:** 27 октября 2026 года.

**Общая архитектура:** [ARCHITECTURE.md](../ARCHITECTURE.md).

## 1. Ответственность компонентов

- Merchants владеет API-ключами: выпуском, защищённым хранением проверочных данных, отзывом и привязкой к мерчанту. Он предоставляет внутренний gRPC-контракт проверки ключа.
- Gateway на YARP выполняет аутентификацию внешних API-ключей через Merchants, получает MerchantId и формирует ClaimsPrincipal. Проверка применяется к маршрутам, требующим доступа backend мерчанта.
- Gateway передаёт проверенный MerchantId целевому сервису. Он не управляет созданием карточных сессий, состояниями платежей или другими бизнес-сценариями.
- CardVault не хранит и не проверяет API-ключи мерчантов. Он устанавливает доверие к вызывающему Gateway, получает контекст мерчанта и выполняет собственную доменную авторизацию.
- Регистрационный Bearer-токен формы проверяет CardVault по своей CardRegistrationSession. Доверенный контекст мерчанта не заменяет этот токен на маршруте регистрации карты.

## 2. Контракт внутреннего контекста

Для идентификации мерчанта используется внутренний HTTP-заголовок `X-Way2Pay-Merchant-Id` с одним непустым GUID. Контекст описывает мерчанта, а не личность покупателя или пользователя админки.

Gateway удаляет клиентские заголовки, выдающие себя за внутренний контекст идентификации, включая любые значения `X-Way2Pay-Merchant-Id`. На маршрутах с успешно проверенным API-ключом он устанавливает одно значение из ClaimsPrincipal. На остальных маршрутах клиентский внутренний контекст не передаётся. Перечень доверенных заголовков явный; добавление новых полей требует такого же удаления и замены.

Исходный API-ключ после проверки не передаётся целевому сервису. Регистрационный Bearer-токен на `/cards` передаётся CardVault для самостоятельной проверки.

Принимающий сервис проверяет сервисную идентичность Gateway до использования заголовка. Отсутствующее, множественное или некорректное значение не создаёт доверенный контекст. Бизнес-обработчики получают контекст через HTTP-границу и не зависят от механизма проверки сертификата.

## 3. Доверие между сервисами

В целевой инфраструктуре используется mTLS с проверкой вызывающего сервиса. Доверие к центру сертификации само по себе недостаточно: получатель должен проверить, что запрос пришёл именно от разрешённой идентичности Gateway. Другой внутренний сервис не получает право подставлять MerchantId только за счёт наличия сертификата.

Для локальной разработки допускается явно включаемый режим без mTLS. Он ограничен Development, не должен допускать доступ недоверенных клиентов к внутренним endpoints и не может использоваться вне Development. Отсутствие сертификата не является автоматическим основанием доверять заголовку.

Service Mesh, JWT и отдельный Auth Service сейчас не вводятся. Подключение mTLS впоследствии меняет установление доверия на транспортной границе, а не бизнес-логику сервисов. Конкретные сертификаты, идентификатор сервиса в сертификате и управление их жизненным циклом ещё проектируются.

## 4. Потоки и ошибки

Создание карточной сессии:

1. Backend мерчанта отправляет запрос через Gateway с API-ключом.
2. Gateway проверяет ключ через Merchants и устанавливает аутентифицированную идентификацию мерчанта.
3. Gateway проксирует исходный запрос в CardVault с проверенным внутренним контекстом.
4. CardVault проверяет доверие к Gateway и создаёт сессию в контексте мерчанта, применяя собственные ограничения.

Регистрация карты: форма отправляет регистрационный Bearer-токен через Gateway в CardVault. Для проверки этого токена вызов Merchants не нужен.

Неверный или отозванный API-ключ приводит к `401`; подтверждённая идентификация без требуемого права — к `403`. Недоступность Merchants при проверке ключа приводит к `503`, а не к сообщению о неверном ключе. При неуспешной проверке запрос не проксируется в бизнес-сервис.

Сервисная аутентификация внутренних вызовов и проверка принадлежности бизнес-объектов сохраняются независимо от аутентификации внешнего API-ключа. Этот ADR не определяет права Connector на раскрытие реквизитов или авторизацию пользователей админки.

## 5. Порядок реализации и открытые вопросы

Следующий этап — минимальный настоящий Merchants с доменной моделью мерчанта и API-ключей, SQL Server persistence и gRPC-контрактом проверки ключа. Временный Development-адаптер проверки ключей в Gateway для этого этапа не используется. Админка, настройки провайдеров и routing не входят в ближайший блок.

После этого подключаются аутентификация Gateway, приём внутреннего контекста и HTTP-выдача регистрационных сессий CardVault. Зафиксированная [точка продолжения CardVault](../progress/CARDVAULT.md) отделяет готовые части от оставшихся задач. Выбранный настоящий Merchants не отменяет отдельный ограниченный Development-режим без mTLS.

Также предстоит определить внешний формат API-ключа, необходимые права ключей, аутентификацию Gateway при вызове gRPC Merchants и конкретное ограничение локального режима без mTLS. Кеширование результатов проверки ключей и сроки применения отзыва этим решением не утверждены.
